# CI/CD через GitHub Actions

Активна конфігурація розташована в `.github/workflows/`:

| Workflow | Запуск | Результат |
| --- | --- | --- |
| `ci.yml` — CI | Push у `main` або ручний запуск | Тести на трьох ОС, звіти JUnit |
| `release.yml` — Desktop release | Push тега `v*` | Тести, три ZIP, новий GitHub Release |
| `release.yml` — Desktop release | Ручний Run workflow | Тести та три ZIP в Actions Artifacts |

Середовища GitHub: Ubuntu 24.04 x86_64, Windows Server 2022 x86_64,
macOS 15 ARM64. На кожному встановлюється Python 3.13. Спільна дія
`.github/actions/setup/action.yml` встановлює залежності з `requirements-lock.txt`
і бібліотеки Qt/X11 та Xvfb для Linux. Windows-залежності PyInstaller мають
платформні маркери в lock-файлі. Виклики Python не залежать від шляхів до venv.
Зовнішні actions зафіксовані повними SHA комітів із коментарями версій.

## Перевірки та артефакти

Тести на Linux і macOS використовують `QT_QPA_PLATFORM=offscreen`, а на Windows —
`windows`, щоб Qt мав доступ до системних шрифтів для текстового PDF.
Відповіді перекладачів підставні. Зібраний застосунок запускається окремо з `--smoke-test`:
він створює вікно та перевіряє запис і читання PDF з українським текстом.
На Linux перевіряється справжній графічний модуль X11 під Xvfb;
на Windows і macOS — системні графічні модулі Qt.

`scripts/package.py --smoke-test` перевіряє запуск і створює переносний ZIP
усієї папки застосунку. Він зберігає символічні посилання й права виконання
macOS та нормалізує назву архітектури Windows `AMD64` до `x86_64`.

Звіти тестів і ZIP зберігаються на сторінці запуску **Actions → Artifacts**
протягом 14 днів. ZIP у GitHub Release зберігаються незалежно від строку
зберігання Actions Artifacts. Невдала платформа не перериває інші, але
за будь-якої невдалої збірки задача публікації не запускається.

## Публікація

Тег повинен містити новий workflow. Після надсилання конфігурації до `main`
створіть новий тег, наприклад `v0.3.0`, і надішліть його до GitHub.
Новий тег запускає збирання саме його коміту. Після успіху всіх платформ
`scripts/github_release.py` виконує публікацію:

- Перевіряє наявність рівно трьох очікуваних ZIP і коміт тега через GitHub API.
- Створює чернетку релізу з автоматичним описом змін або знаходить наявний реліз.
- Завантажує пакети та перевіряє їхні розміри й SHA-256 за відповіддю GitHub.
- Публікує чернетку лише після перевірки всіх трьох пакетів.

Підпис кожного пакета містить назву файлу та `git:<коміт>`. Повторний запуск
пропускає вже завантажені пакети з тим самим комітом і продовжує чернетку після
часткового збою. Наявні файли з невідомим походженням, іншим комітом або
незавершеним завантаженням автоматично не перезаписуються та не видаляються.
Назва й опис уже створеного користувачем релізу зберігаються.

Задачі тестування та збирання мають лише `contents: read`. Тільки задача
публікації має `contents: write` й отримує автоматичний `GITHUB_TOKEN`.
Окремий PAT чи секрет у налаштуваннях репозиторію не потрібний.
Публікація звертається лише до офіційних API GitHub і не передає токен через
аргументи команд або перенаправлення HTTP. Ручний запуск не публікує реліз.

## Міграція з Jenkins

Задачі `desktop-pdf-translator` і `desktop-pdf-releases` у наявному Jenkins
вимкнені, щоб уникнути подвійних збірок і публікацій. Їхні старі артефакти
залишаються в Jenkins, а попередні GitHub Releases залишаються доступними.
Файли конвеєрів, налаштувань агентів і початкового розгортання вилучено
з актуальної версії репозиторію; вони збережені в історії Git до міграції.

Інші Jenkins-задачі та служби VPS не змінюються. Новий CI/CD не залежить
від локального Mac, SSH-тунелю чи агентів Jenkins.
